PRODUCT INTRO

产品简介

不只是"套皮聊天"，而是由人物档案与史料知识库双重驱动的真实还原

本产品是一个"与历史人物对话"的 Web 应用：用户可以从 97 位覆盖上古至民国的历史人物中任选一位，以自然语言与其沉浸式对话。

  • 人物由人物档案（YAML）+ 史料知识库（RAG）双重驱动，还原人物性格与说话风格；
  • 回答基于真实史料检索增强生成，带知识溯源（显示参考史料），内置多条防幻觉规则；
  • 支持多轮上下文记忆、SQLite 持久化、对话导出，刷新 / 重开页面不丢失；
  • 提供水墨丹青风格的 Streamlit 界面，可一键部署到 Streamlit Cloud 在线体验。
一句话定位：一个具备"人物角色 + 史料问答 + 知识溯源 + 持久化 + 工程健壮性"的完整生产级历史人物 RAG 对话系统。

FEATURES

核心功能

八大能力，覆盖从对话到知识库运维的完整闭环

一

🎭 角色扮演

97 位历史人物，覆盖 21 个朝代。每位人物由独立 YAML 档案定义身份、性格、说话风格与名言，系统提示词据此生成，口吻与时代感真实还原。

二

📚 RAG 知识增强与溯源

内置双轨史料库（206 篇 = 99 persona + 107 真实史源），97/97 人物均有真实史料（古诗文网 / 百度百科 / ctext），检索增强生成，回答末尾自动标注【参考史料】，支持知识溯源。

三

💬 多轮对话与记忆

内存记忆（最近 10 轮）+ SQLite 双层结构；记忆按 "会话:人物" 复合键隔离，多用户、多人物互不串扰。

四

💾 对话持久化与管理

SQLite（WAL 模式）存储对话与会话消息，刷新、切换人物、重开应用均不丢失；支持历史列表、继续对话、删除对话。

五

📤 对话导出

一键将对话导出为 Markdown / PDF 格式下载。

六

🌐 Web 界面

Streamlit 构建的水墨丹青界面：人物按朝代折叠选择、人物档案展示、聊天界面、最近对话与推荐人物。

七

🛠️ 知识库工具链

史料爬虫（crawl_knowledge / crawl_history）、知识生成（generate_knowledge）、向量库构建（build_vector_db）脚本，支持知识库扩展。

八

🧪 工程化与测试

110 个 pytest 用例（人物加载、知识库完整性、RAG 防污染、多人物联合检索、BM25、多格式解析、端到端等），Dev Container + Streamlit Cloud 部署支持。

亮点特色

产品级还原 × 工程级健壮，demo 与生产之间的距离被逐一填平

🏮

产品级亮点

  • 历史还原与防幻觉并重——史料明确记载的照实回答，未记载的如实说明，绝不编造年份、数字或文献出处；
  • 近零成本——LLM 用低成本 deepseek-v4-flash，Embedding 用本地 HuggingFace 模型，无需额外 API Key；
  • 跨人物问答不串味 + 多人枚举联合召回——向李白问杜甫自动退回全局检索；问"李白和杜甫谁更豪放"这类点名多人的题走联合检索（$in 联合池），不把当事人传记误当史料注入；
  • 开箱即用——向量库随仓库提交，本地缓存模型时首次启动无需联网。
⚙️

工程级亮点

  • 版本严格钉死——如 chromadb==1.5.8，与向量库构建环境一致，规避 0.x/1.x 格式不兼容；
  • 云端部署兼容——Streamlit Secrets 自动桥接为环境变量，解决云端密钥读取问题；
  • 健壮 API 调用——超时控制、指数退避重试、区分网络 / 密钥 / 通用错误的友好提示；
  • Embedding 离线加载优化——自动解析本地模型快照，避免联网校验挂起数十秒甚至超过 200 秒。

CONVERSATION FLOW

对话 / RAG 流程

从选择人物到知识溯源，八步走完一次完整对话

1
选择人物
加载 YAML 档案，生成人物系统提示词（身份、性格、说话风格、知识领域、名言）。
2
用户输入
新对话则创建 conversation 记录。
3
记忆恢复
按 会话:人物 复合键读取内存记忆，为空则从 SQLite 恢复最近 10 轮。
4
RAG 检索
① 多人物联合检索（点名 ≥2 人走 $in 联合池）→ ② 人物过滤 / 全局检索 + 决策门 → ③ 库外或无相关走 no-RAG 分支 → ④ 拼装上下文与溯源列表。
5
组装消息
System Prompt（人物设定 + 史料 + 4 条防幻觉规则）+ 历史消息 + 当前问题。
6
调用 LLM
超时控制 + 指数退避重试，区分错误类型友好提示。
7
持久化
助手消息连同引用来源 JSON 写入 SQLite，并更新内存记忆。
8
前端展示
展示回复内容 + 参考资料，支持导出 / 清空 / 更换人物。

KEY DESIGNS

关键技术特色

六个设计决策 —— 代码里看不出来缘由的部分，这里讲清楚

一

检索相关性阈值，杜绝跨人物史料污染 FILTERED_SCORE_RATIO = 1.25

按人物过滤检索的语义距离若明显劣于全局最优，说明问题与本人物无关，自动退回全局检索。
解决的问题：向李白问"杜甫的诗"，原本会命中李白自己的传记（自传在"李白"过滤下必然得分最高），被当作"相关史料"注入导致引用错误。
实测效果：同人检索距离比 ~1.0，跨人 ~1.83，阈值可清晰区分。对应测试见 tests/test_retrieval.py。
二

会话记忆复合键 session_id:character_name

内存记忆与数据库归属均以"会话 + 人物"双重维度隔离，多用户、多角色不串记。对应测试见 tests/test_memory.py。
三

Embedding 离线加载 _resolve_embedding_model

新版 huggingface_hub 的 hf_hub_download 默认 local_files_only=False，会忽略 HF_HUB_OFFLINE 环境变量并强制联网校验，在受限网络下可挂起超过 200 秒。
方案：自动把模型解析为本地缓存快照路径后加载（约 5 秒），并顺带启用离线环境变量；本地无缓存时退回正常下载。对应测试见 tests/conftest.py。
四

系统提示词 4 条硬性防幻觉规则

① 以史料为准，不增删虚构细节；② 史料未记载的明确说明，不编造史实 / 年份 / 数字 / 文献；③ 引用仅限检索到的史料列表；④ 保持人物口吻但事实必须准确。
无 RAG 命中时进入专门分支："基于可靠常识 + 切勿编造出处 / 数字"。对应测试见 tests/test_agent_prompt.py。
五

低成本部署方案

LLM 用 deepseek-v4-flash（低成本）+ Embedding 本地化（零 API 成本）+ 向量库随仓库提交（免首次构建），实现"近乎零成本运行 + 云端可部署"。
六

版本钉死与兼容性

requirements.txt 明确标注各关键包必须版本（尤其 chromadb==1.5.8 不可降到 0.x，与已提交向量库格式匹配），并说明与构建环境一致，避免线上 / 线下格式不兼容。

ROADMAP

局限与展望

知道边界在哪里，才能走得更远

🧱

当前局限

  • 97/97 人物均有真实史源，但以列传 / 章节节选为主，单篇深度有限，冷门细节覆盖仍不足；
  • 21 篇百度百科为三手资料（非正史原文），权威性低于古籍原文，如实标注、仅作引用溯源；
  • LLM 依赖外部 API（需联网），本地仅 Embedding 离线；在线生成指标为真实 DeepSeek 实测，Faithfulness 0.227 仍有提升空间。
🚀

可扩展方向
